# cost-control MVD 设计 v2：与 Kimi 方案的合并修订

> 评审对象：`cost-control-mvd-design.md`（Kimi，2026-10-31，394 行）
> 评审人：本项目实现者
> 结论：方向采纳，口径与顺序做 8 处修订、补 4 条缺失主线

---

## 0. 一句话结论

Kimi 把项目从"成本计算器"推向"岗位替代"，骨架是对的：**单据不可变、月结分步、预警待办、月末包**。但有三个问题必须先修：

1. **约当产量的口径错了**（§1.2）：把"期初在产品约当"加进分母会重复计算，单位成本会被系统性低估（示例场景低估 29%–50%）；
2. **与现有引擎/校验有硬冲突**：负数分录被 `accounting.py` 直接拒绝、跨期冲销在"期间隔离"的数据集里验不到原单、`receipts`（完工入库）在模型里根本不存在；
3. **缺一条主线**：只结转了"在产成本"，没有结转"总账余额"。没有 5001 的期初，下一期的试算平衡必然断裂——这恰恰是 Kimi 想宣称的"能代替记账"的前提。

以下按"同意 / 反对 / 补充"逐条展开，然后给出修订后的模型、顺序与验收。

## 2. 逐条辩论

### 2.1 约当产量：把"期初约当"加进分母会系统性低估单位成本

Kimi 写的是：

> 下期计算：工单累计成本 = 期初在产 + 本期归集；约当产量用**累计口径**（期初在产品约当 + 本期发生约当）。

这句话有两种读法。如果只是"分子含期初"，那没问题；但"分母也加期初约当"就是重复计算——同一批在产品的成本与产量各算了一次。按字面推一遍（用 PO-1004 的在产结构：上期投产 200，完工 150、报废 3，期末在产 47；材料 100%、加工 40%）：

```text
上期沉淀：材料 2,095.35、加工 117.49
本期只做加工把 47 件做完，不再领料：本期加工 176.25

正确（加权平均）：
  材料约当量 = 47（全部完工）          → 单位材料 = 2,095.35 / 47 = 44.58
  加工约当量 = 47                      → 单位加工 = (117.49 + 176.25) / 47 = 6.25

Kimi 口径（期初约当再加一次）：
  材料约当量 = 47 + 47 = 94            → 22.29（低 50%）
  加工约当量 = 47 + 47×40% = 65.8      → 4.46（低 29%）
```

偏差不是小数：它会让完工产品成本少计近一半的材料费，并顺着半成品结转传进成品。

**正确的公式**（加权平均法，也是教材里"月初在产品成本 + 本月发生费用"的标准写法）：

```text
材料约当量 = 本期完工 + 报废 + 期末在产 × 投料程度
加工约当量 = 本期完工 + 报废 + 期末在产 × 完工程度
单位成本   = (期初成本 + 本期发生) / 约当量
完工成本   = 单位成本 × (完工 + 报废)
期末在产   = 总成本 − 完工成本
```

期初在产品已经包含在"本期完工"或"期末在产"里，**分母不需要也不应该再加一次**。

**但差异分析是另一回事。** 如果总成本含期初，而用量差异仍按"标准用量 × 全量约当"比，跨期工单会凭空产生一笔巨额"节约"（期初已投的料没在本期领）。所以差异必须换增量口径：

```text
本期材料约当量（差异用） = 完工 + 报废 + 期末在产×投料程度 − 期初在产×期初投料程度
本期加工约当量（差异用） = 完工 + 报废 + 期末在产×完工程度 − 期初在产×期初完工程度
```

一句话：**定价用加权平均（含期初），考核用增量口径（扣期初）**。Kimi 的 §1.4.4 只说了"期初不参与用量比较"，没给出可执行的公式，这里补上。

代价是：六项差异不再与"工单总差异"严格闭合，期初沉淀的差异只在工单总差异层面体现。这不是 bug，是口径设计，报表里必须写明。Kimi 的 §1.6 已经意识到这一点，保留。

### 2.2 FIFO 还是加权平均：MVD 选加权平均

Kimi 的"先进先出思想"在会计上成立，但代价被低估了：

- FIFO 要把约当量拆成三段：`期初在产×剩余完工比例 + 本期投产本期完工 + 期末在产×完工程度`；
- 每一段要单独留成本层，完工时按层结转；
- 六项差异要按层计算，现有 `costing.py` 的差异行结构装不下。

而现有引擎对**半成品结转**用的就是全月一次加权平均。期初在产再用 FIFO，等于同一套账里两种计价方法并存，解释成本极高。

**结论**：MVD 统一加权平均；FIFO 作为以后的 `costing_method` 选项，需要独立的成本层表，不放进这一版。

### 2.3 "关账快照不可重跑"与解锁流程冲突

Kimi 的 §1.4.1：快照是关账的副作用，独立命令不可重跑，保证"结完账又改数"不可能。

出发点是好的，但和现有流程冲突：`--unlock` 的目的就是返工，返工后重新关账必须重写快照，否则下期读到的是旧在产。更现实的坑是**关账和写快照不在一个事务里**——现在 CLI 是：

```python
report = close_period(run)          # 纯计算，不写库
store.set_status(period, CLOSED)    # 另一个操作
```

两步之间崩溃，就会得到"已关账、无快照"的期间，下一期直接断链。

**修订**：

- 关账做成一个仓储方法：`store.close_period(period, run, journal)`，在一个 SQLite 事务里写 **状态 + 在产快照 + 下期期初余额 + 审计日志 + 步骤记录**；
- 快照按 `(period, order_no)` 幂等覆盖：重复关账结果一致，解锁返工后重写；
- "不可重跑"改成"**CLOSED 状态下不可静默重算**"，重算必须显式 `--reopen`，并留审计。

### 2.4 负数分录：现有代码会直接报错

Kimi 的 §3.3.5 要求冲销单生成负数分录、借贷不变号。但 `accounting.py:39` 现在是这样：

```python
if self.debit < 0 or self.credit < 0:
    raise ValueError("分录金额不能为负数")
```

而且 `entry.is_balanced` 要求 `debit_total > 0`，全红字凭证会被判为不平衡。

两种改法：

| 方案 | 做法 | 评价 |
|---|---|---|
| A 换方向 | 冲销借方改成贷方 | 数值等价，但丢掉"红字"语义，无法从凭证看出这是冲销 |
| B 红字 | `direction` + 有符号 `amount` | 保留红字习惯，需要改模型与报表 |

选 **B**。新的分录模型：

```python
@dataclass(frozen=True)
class JournalLine:
    account: str
    summary: str
    direction: str      # "D" / "C"
    amount: Decimal     # 允许负数（红字）

    @property
    def debit(self) -> Decimal:
        return self.amount if self.direction == "D" else ZERO

    @property
    def credit(self) -> Decimal:
        return self.amount if self.direction == "C" else ZERO
```

`is_balanced` 改为 `debit_total == credit_total` 且绝对值大于 0；试算表继续用有符号合计，红字天然抵消。影响面：`accounting.py`、`report.py`、`web.py` 的凭证渲染、以及 4 组凭证测试。

### 2.5 跨期冲销：本期 Dataset 看不到上期单据

Kimi 说"已结账期间的原单不可在当期冲销，必须在本期做红字冲销单"。方向对，但实现层有个洞：`dataset.py` 的校验只看本期数据，`reverses` 指向的上期单据根本不在内存里，没法验证"原单存在、未超冲"。

**补充**：一张全局单据注册表（不按期间分区）：

```sql
CREATE TABLE doc_refs (
  doc_no     TEXT PRIMARY KEY,
  period     TEXT NOT NULL,
  kind       TEXT NOT NULL,      -- ISSUE / LABOR / OVERHEAD / RECEIPT / ADJUST
  order_no   TEXT,
  material   TEXT,
  qty        TEXT,               -- 原单数量，用于剩余可冲额度
  amount     TEXT,
  status     TEXT NOT NULL       -- ACTIVE / REVERSED
);
```

导入时写、冲销时查、超冲时拒。`dataset.validate` 拿不到跨期信息，所以校验要上移到 `importer/store` 层，或者给 dataset 注入一个只读的 `doc_index`。

### 2.6 CSV 模板的三处硬伤

Kimi 的模板清单看起来齐，但对着模型一查就漏：

| 问题 | 后果 |
|---|---|
| `labor_YYYYMM.csv` 只有 order/hours/rate，**没有 cost_center** | 人工无法归集到成本中心，制造费用分配动因直接为零；这是必填字段 |
| `receipts_YYYYMM.csv`（完工入库）没有对应模型 | 现在完工数量挂在 `orders.qty_completed` 上，没有入库单据；引入它要改归集入口，属于新 Slice，不是"模板" |
| `order_id`、`qty INTEGER` | 模型里是 `order_no`、`Decimal(4 位)`；半成品 0.816 kg 这类数量存不进 INTEGER |

**修订**：报工模板补 `cost_center`、`operation`；本版不引入完工入库单据（工单完工数量继续作为输入），把 receipts 列为独立 Slice；所有数量列统一 TEXT/Decimal；字段名对齐 `order_no / doc_no / material`。

### 2.7 调整单审批阈值笔误

原文："调整单金额 ≤ 0 需主管审批"。金额为负才审批，等于放过所有正数调整。应为：

```text
|amount| ≥ adj_approval_threshold（默认 500.00）→ 必须 approved_by，且审批人 ≠ 创建人
```

### 2.8 缺失的主线：总账余额跨期结转

这是最关键的补充。Kimi 只结转了"在产成本"，但下一期的试算平衡需要**全部科目**的上期期末余额：

```text
2026-10 关账后              2026-11 期初（应自动带入）
1002  497,600.00  借    →    1002  497,600.00
1403   53,212.60  借    →    1403   53,212.60
1405  150,879.15  借    →    1405  150,879.15
1406    6,653.78  借    →    1406    6,653.78
5001    2,345.47  借    →    5001    2,345.47   ← 必须等于 Σ wip_opening
1602  −61,380.00  贷    →    1602  −61,380.00
2211  −34,571.00  贷    →    2211  −34,571.00
4001 −615,000.00  贷    →    4001 −615,000.00
6602      260.00  借    →    6602      260.00
```

两条硬校验：

1. `5001 期初 == Σ wip_opening.cost_material/labor/oh`，差一分钱就拒绝关账；
2. 带入后的期初余额借贷合计为 0。

没有这两条，Kimi 的 §1.4.3 守恒公式（期初 + 本期归集 ≡ 完工 + 期末在产）在账务层根本无法验证——因为 5001 的期初根本不存在。

### 2.9 缺失的控制：数据指纹与步骤失效

Kimi 的 §4.2 说"步骤只可前进，回退=重算"，但没处理**静默改数**：第 3 步计算快照做完，有人又导入了一张领料单，第 4–8 步仍然显示绿色，关账时用的是旧快照。

**补充**：每个期间存一个数据指纹，步骤记录指纹，过期即失效。

```text
fingerprint = sha256(
  orders + issues + labor + overhead + params + opening_balances + std_version
  按主键排序后的规范化 JSON
)
```

规则：

- 第 3 步（计算快照）记录指纹；
- 第 4–8 步执行前比对当前指纹，不一致 → 步骤状态置 `STALE`，阻塞并提示"数据已变更，请从第 3 步重算"；
- 重算作废下游步骤，写审计。

这条补上之后，Kimi 的"回退=重算"才真的成立。

### 2.10 权限：审计先行，认证后置

Kimi 把"用户认证 + 会话"放在第 5 位（附录 A）。我的判断相反：

- **审计日志**便宜且立刻有用：谁导入了什么、谁改了容差、谁关的账。没有它，后面每个功能都缺责任链；
- **认证**在本地单用户场景收益很低，却要自己实现 session、cookie、CSRF、口令策略，攻击面反而变大；
- CLI 的 `CC_USER` 只是**署名**，不是认证；把它称作"身份"会误导。

**修订**：审计并入 Slice A（和关账事务一起做）；认证/角色放到 Slice G，且坚持"默认只监听 127.0.0.1，写操作要显式开启"。

## 3. 修订后的口径与模型

### 3.1 期初在产：用"剩余量工单"，引擎改动最小

两种建模：

| 方案 | 做法 | 影响 |
|---|---|---|
| A 剩余量工单 | 下期工单 `qty_planned = 剩余数量`（如 47），完工即清零；期初成本作为独立字段并入成本池 | `costing.py` 只改分子与守恒式；约当量公式不变 |
| B 累计量工单 | 工单数量跨期累计，完工数累加 | 每期要算"本期完工 = 累计差"，约当量、状态、报表全要改 |

选 **A**。它保持"一个期间一套单据"的现有边界，跨期只多一个 `carried_from` 和期初成本字段。

数据模型（修正 Kimi 的 qty 类型与字段）：

```sql
CREATE TABLE wip_opening (
  period         TEXT NOT NULL,          -- 期初所属期间
  order_no       TEXT NOT NULL,
  product        TEXT NOT NULL,
  qty_planned    TEXT NOT NULL,          -- 下期计划（= 剩余量）
  qty_completed  TEXT NOT NULL,          -- 截至上期累计完工（追溯用）
  qty_in_wip     TEXT NOT NULL,          -- 期末在产数量
  eq_material    TEXT NOT NULL,
  eq_conversion  TEXT NOT NULL,
  cost_material  TEXT NOT NULL,
  cost_labor     TEXT NOT NULL,
  cost_oh        TEXT NOT NULL,
  std_version    TEXT,                   -- 继承开工版本
  carried_from   TEXT NOT NULL,
  fingerprint    TEXT NOT NULL,
  PRIMARY KEY (period, order_no)
);
```

工单新增：`carried_from`、`std_version`、`opening_material/labor/oh`（或由 wip_opening 关联）。

成本计算：

```text
工单总成本 = 期初(material+labor+oh) + 本期归集
单位成本   = 总成本 / 约当量（公式见 §2.1）
完工成本   = 单位成本 × (完工 + 报废)
期末在产   = 总成本 − 完工成本
守恒       = 期初 + 本期归集 ≡ 完工 + 期末在产
```

### 3.2 关账事务

```python
with store.transaction():
    snapshot = store.build_wip_snapshot(run)      # 仅未完工工单，按要素
    opening = store.build_next_opening(run)       # 全部科目期末余额
    store.assert_reconcile(snapshot, opening)     # 5001 == Σ wip
    store.write_wip_opening(next_period, snapshot)
    store.write_opening_balances(next_period, opening)
    store.set_period_status(period, CLOSED)
    store.record_steps(period, ...)
    store.audit("CLOSE", period, {...})
```

失败整体回滚，不会出现"关了一半"。

### 3.3 单据与冲销

- `doc_refs` 全局注册表（§2.5）；
- 冲销单：`reverses` 必填、同 `order/material`、`|qty| ≤ 原单剩余可冲量`、`period ≥ 原单期间`；
- 已 CLOSED 期间的原单允许跨期冲销，冲销单计入本期；
- 调整单：`element + amount + reason_code`，`|amount| ≥ 阈值` 时必须 `approved_by ≠ created_by`；
- 凭证：红字分录（§2.4），`REVERSAL-HEAVY` 提示规则。

### 3.4 数据指纹与步骤

```sql
CREATE TABLE period_steps (
  period      TEXT NOT NULL,
  step        INTEGER NOT NULL,
  status      TEXT NOT NULL,       -- DONE / STALE / BLOCKED
  fingerprint TEXT,
  operator    TEXT,
  done_at     TEXT,
  note        TEXT,
  PRIMARY KEY (period, step)
);
```

### 3.5 迁移

现有库是 `schema_version = 1`，v2 至少涉及：

- `orders` 加 `carried_from / std_version`；
- `issues / labor / overhead` 加 `reverses / batch_id`；
- 新表 `wip_opening / doc_refs / adjustments / alerts / period_steps / audit_log`。

规则：升级前自动 `VACUUM INTO backup-<version>-<ts>.db`；`ALTER TABLE ADD COLUMN` 可在事务内完成；迁移脚本按 `meta.schema_version` 幂等执行。**不要**让用户手工改库。

## 4. 修订后的实施顺序

| Slice | 内容 | 依赖 | 验收标准 |
|---|---|---|---|
| **A 期初与总账链** | §1 + §2.8 + §3.2 + 审计最小集 + 迁移 | 无 | 两期 fixture：10 月关账 → 11 月期初自动带入；5001 期初 = Σ 在产；跨期工单守恒；解锁重关幂等 |
| **B 冲销与调整** | §3 + doc_refs + 红字分录重构 | A（要有关账事务与审计） | 冲销净额守恒；超冲拦截；跨期冲销计入本期；红字凭证借贷仍平 |
| **C CSV 导入** | §2 + dry-run + 模板 + 编码兜底 | B（负单/冲销校验） | 行级错误定位；整批回滚；Excel 另存 GB18030 可读 |
| **D 月结包** | §8 | A（要有关账结果） | 一个目录回答"多少钱、为什么、谁确认的、账平不平" |
| **E 预警 + 操作台** | §6 + §4 + 指纹 | C、D | 预警状态流转；步骤跳步拦截；改数后步骤变 STALE |
| **F 标准版本** | §5 | A | 工单锁版本；跨期继承；历史版本可查 |
| **G 认证与角色** | §7 | E | 三角色路由校验；登录失败入审计 |

与 Kimi 的顺序差异及理由：

1. **月结包从第 8 提到第 4**：它是纯输出、零状态、风险最低，却能最快形成"可交付物"；也顺带把 CSV 导出工具做出来，C 和 D 复用。
2. **预警与操作台合并**：操作台第 4 步就是"预警清零"，拆成两个 Slice 会返工。
3. **审计提前**：它便宜，且是后面所有动作的底座。
4. **认证后置**：见 §2.10。

MVD 的可宣称边界也随之调整：**A + B + C 做完，才能说"能代替成本会计的计算与记账"**（Kimi 的 1→2→3 少了总账链，记账是断的）；**再加 D + E，才能说"能走完一个月结"**。

## 5. 验收与测试增量

在 Kimi 附录 B 的基础上补：

- **两期链路 fixture**：10 月 PO-1004 在产 47 件、期初 2,212.84 → 11 月完工 47 件，验证单位成本、守恒、5001 余额、下期期初；
- **口径回归**：同一批数据分别用"含期初加权平均"和"旧的全量口径"跑，断言前者单位成本更高、差额可解释（防止 §2.1 的重复计算回归）；
- **红字平衡**：构造一张全额红冲的领料单，断言凭证借贷合计仍相等、试算表合计为 0；
- **跨期冲销**：对 CLOSED 期间的领料单在本期冲销，断言本期差异包含该影响；
- **指纹失效**：第 3 步后插入一张领料单，断言第 4–8 步变 STALE 并阻断关账；
- **迁移**：v1 库升级到 v2 后，旧期间数据可读、计算结果不变。
